# Git attack (Bandit 27, 28, 29, 30, 31)


## The concept
During the execution of the levels 27-31, it was possible to understand the real meaning of Git inside a project, because before making use of it, I thought it was something optional to a team of developers (just an example of a group of people that need to use it), when it actually means the necessity of saving every part of a project in different ways, for security and for searching uses. But using Git doesn't bring only good things, it can also be used as an attacking weapon, because having all the registers of what was written since the beginning of a project can be really dangerous when known by the wrong people. The Git can hide secrets in places the command "cat" can't look at, the names of these places are old commits, branches and tags.

## How it works
The first way of looking to the past of a project using Git is by making usage of the command "git log", that allows us to take a look on the old commits that were done. It is possible to see the hash of the commit, what was written, who wrote it and when was it committed. It is really important to be cautious when using the commit in a project that contains sensitive content inside it, such as passwords, private keys or important concepts that couldn't be seen by other people, because if someone with wrong intentions gets access to the git repository, they can look at all the sensitive content by using the hash and the command "git show <hash>". The second way to find hidden information is by using the command "git branch -a", that shows all the branches (including the non-default ones), what makes it possible to change branches whenever they want by using the command "git checkout <branch>" and gets access to different kinds of information by doing that. The information was always there, it was only necessary to look to the right place to find it (everything comes together when cloning the repository, but not everything is visible in the first look). The third way is by using the tags, that can be found with the command "git tag", making it possible to look inside every tag with the command "git show <tag>", then looking inside the tag, where sensitive information can be hidden. All these elements are powerful weapons that can be used by both sides, what makes them so dangerous, so it is important to manage what stays saved after every commit, inside every branch and in every tag inside the repository.

## The diagnostic path
When an attacker is searching for sensitive information, he may look at the messages that appear when using the command "git log", because in most of the cases it brings key words about what the commit was about. When the commits don't bring you the information you were looking for, it may be time to change the branch you are looking at, so you will face different information that may be useful. If the information you are looking for is not in any of the branches you looked at, maybe it's time to look in the tags, where the information can also be hidden from you. In the level 28, when looking for the password, I found the commit called "initial" that didn't have any important information for me in that specific level, so I took a look at the other commit names, then I discovered that I was looking at the wrong commit.
## Real-world relevance
Attackers tend to look everywhere inside the repository to find the specific password they are looking for, and it actually happens in real life at big companies. The fact that many employees tend to reuse the same password for different accounts can cause even more problems to the company and more advantages to the attacker, because when an attacker discovers a password when looking inside the repository, he has finished his job, everything since that moment becomes extremely easy for them, because they already got the sensitive information they were looking for. It is also common to see employees thinking that using the ".gitignore" is a security control, when in reality, it doesn't protect the system, it only works for some specific moments, and if the attacker knows a little bit about what he is doing, he will be able to find a way even with the .gitignore trying to put him down. Leaked secrets should be rotated/revoked, and not only deleted, it doesn't protect anything, because it keeps existing in the old commits and in every copy. There are some tools in the market that automate the work of trying to find the sensitive information inside repositories, such as gitleaks, trufflehog and git-secrets. I did manually what these tools automate. These behaviors map to known MITRE ATT&CK techniques: T1078 (Valid Accounts) and T1552.001 (Credentials In Files).

## Key commands
- `git log` - shows all the past commits
- `git show <hash>` - shows a specific commit you choose
- `git branch -a` - shows all the existing branches
- `git checkout <branch>` - switches to the branch you choose
- `git tag` - shows all the tags
- `git show <tag>` - shows the content of that tag
